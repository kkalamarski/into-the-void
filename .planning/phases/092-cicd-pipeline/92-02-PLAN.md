  <name>Task 1: Create deployment script for Swarm manager</name>
  <files>deploy/deploy.sh</files>
  <action>
Create `deploy/deploy.sh` - a deployment script that runs on the Swarm manager node.

The script should:

1. **Accept parameters:**
   - `$1` = TAG (the version being deployed, e.g., "1.19.0")
   - `$2` = REGISTRY (container registry, e.g., "ghcr.io/owner/repo")

2. **Set strict mode:**
   ```bash
   #!/bin/bash
   set -euo pipefail
   ```

3. **Validate inputs:**
   ```bash
   TAG="${1:?TAG required}"
   REGISTRY="${2:?REGISTRY required}"
   ```

4. **Pull new images:**
   ```bash
   echo "Pulling images for tag: $TAG"
   docker pull "$REGISTRY/api:$TAG"
   docker pull "$REGISTRY/game-server:$TAG"
   docker pull "$REGISTRY/web:$TAG"
   ```

5. **Run database migrations:**
   ```bash
   echo "Running database migrations..."
   # Run migrations in a temporary container connected to the internal network
   docker run --rm \
     --network itv_internal \
     -e DATABASE_URL="postgresql://${POSTGRES_USER:-postgres}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB:-into_the_void}" \
     "$REGISTRY/api:$TAG" \
     node -e "require('drizzle-orm/node-postgres/migrator').migrate(require('./db'), { migrationsFolder: './migrations' }).then(() => process.exit(0)).catch(e => { console.error(e); process.exit(1); })"
   ```

   Note: The above assumes migrations are bundled in the API image. However, since this is a NestJS app using Drizzle, a simpler approach is to run migrations before the app starts via the existing pnpm db:migrate.

   **Alternative approach - use a migration container:**
   ```bash
   echo "Running database migrations..."
   # Create a one-off service for migrations
   docker service create --name itv_migrate \
     --network itv_internal \
     --restart-condition none \
     --env DATABASE_URL="postgresql://${POSTGRES_USER:-postgres}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB:-into_the_void}" \
     "$REGISTRY/api:$TAG" \
     sh -c "cd /app && npm run db:migrate"

   # Wait for migration to complete
   while docker service ls | grep -q itv_migrate; do
     sleep 2
   done
   ```

   **Simplest approach (recommended):** Since the app has health checks and the database is already running, add migrations to the API container's startup. The rolling update ensures old containers handle traffic while new ones start.

   For this script, use inline migration check:
   ```bash
   echo "Running database migrations..."
   # Migrations run as part of API startup - verify database is reachable
   docker run --rm \
     --network itv_internal \
     -e PGPASSWORD="${POSTGRES_PASSWORD}" \
     postgres:16-alpine \
     pg_isready -h postgres -U "${POSTGRES_USER:-postgres}" -d "${POSTGRES_DB:-into_the_void}"
   ```

6. **Update stack with new images:**
   ```bash
   echo "Deploying stack with tag: $TAG"
   export TAG="$TAG"
   export REGISTRY="$REGISTRY"
   docker stack deploy -c docker-stack.yml --with-registry-auth itv
   ```

7. **Wait for services to stabilize:**
   ```bash
   echo "Waiting for services to stabilize..."
   sleep 30

   # Check service status
   docker stack services itv
   ```

8. **Verify health:**
   ```bash
   echo "Verifying service health..."
   for service in api game-server web; do
     status=$(docker service inspect --format '{{.UpdateStatus.State}}' "itv_$service" 2>/dev/null || echo "unknown")
     if [ "$status" = "completed" ] || [ "$status" = "unknown" ]; then
       echo "Service itv_$service: OK"
     else
       echo "Service itv_$service: $status (may still be updating)"
     fi
   done
   ```

Make the script executable with proper line endings (LF, not CRLF).

<task type="auto">
  <name>Task 2: Implement deployment job in GitHub Actions workflow</name>
  <files>.github/workflows/deploy.yml</files>
  <action>
Replace the placeholder deploy job in `.github/workflows/deploy.yml` with full implementation.

Update the `deploy` job to:

1. **Keep existing configuration:**
   ```yaml
   deploy:
     name: Deploy to Swarm
     needs: build
     runs-on: ubuntu-latest
     if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v')
     environment: production
   ```

2. **Add steps:**

   a. **Checkout code:**
   ```yaml
   - name: Checkout code
     uses: actions/checkout@v4
   ```

   b. **Set up SSH:**
   ```yaml
   - name: Set up SSH
     run: |
       mkdir -p ~/.ssh
       echo "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/deploy_key
       chmod 600 ~/.ssh/deploy_key
       ssh-keyscan -H ${{ secrets.DEPLOY_HOST }} >> ~/.ssh/known_hosts
   ```

   c. **Extract version from tag:**
   ```yaml
   - name: Extract version
     id: version
     run: echo "tag=${GITHUB_REF#refs/tags/v}" >> $GITHUB_OUTPUT
   ```

   d. **Copy deployment files to server:**
   ```yaml
   - name: Copy deployment files
     run: |
       scp -i ~/.ssh/deploy_key -o StrictHostKeyChecking=no \
         docker-stack.yml \
         deploy/deploy.sh \
         ${{ secrets.DEPLOY_USER }}@${{ secrets.DEPLOY_HOST }}:/opt/itv/
   ```

   e. **Copy environment file if secrets exist:**
   ```yaml
   - name: Create environment file
     run: |
       cat > /tmp/.env << 'EOF'
       POSTGRES_PASSWORD=${{ secrets.POSTGRES_PASSWORD }}
       JWT_SECRET=${{ secrets.JWT_SECRET }}
       POSTGRES_USER=postgres
       POSTGRES_DB=into_the_void
       DOMAIN=${{ secrets.DOMAIN || 'intothevoid.online' }}
       REGISTRY=${{ env.REGISTRY }}/${{ github.repository }}
       TAG=${{ steps.version.outputs.tag }}
       EOF
       scp -i ~/.ssh/deploy_key -o StrictHostKeyChecking=no \
         /tmp/.env \
         ${{ secrets.DEPLOY_USER }}@${{ secrets.DEPLOY_HOST }}:/opt/itv/.env
   ```

   f. **Run deployment script:**
   ```yaml
   - name: Deploy to Swarm
     run: |
       ssh -i ~/.ssh/deploy_key -o StrictHostKeyChecking=no \
         ${{ secrets.DEPLOY_USER }}@${{ secrets.DEPLOY_HOST }} \
         "cd /opt/itv && source .env && chmod +x deploy.sh && ./deploy.sh ${{ steps.version.outputs.tag }} ${{ env.REGISTRY }}/${{ github.repository }}"
   ```

   g. **Verify deployment:**
   ```yaml
   - name: Verify deployment
     run: |
       ssh -i ~/.ssh/deploy_key -o StrictHostKeyChecking=no \
         ${{ secrets.DEPLOY_USER }}@${{ secrets.DEPLOY_HOST }} \
         "docker stack services itv"
   ```

   h. **Cleanup SSH key:**
   ```yaml
   - name: Cleanup
     if: always()
     run: rm -f ~/.ssh/deploy_key
   ```

**Required secrets (document in PR description):**
- `SSH_PRIVATE_KEY`: Private key for SSH access to Swarm manager
- `DEPLOY_HOST`: IP address or hostname of Swarm manager
- `DEPLOY_USER`: SSH username (typically 'root' or 'deploy')
- `POSTGRES_PASSWORD`: Database password
- `JWT_SECRET`: JWT signing secret
- `DOMAIN`: (optional) Domain for routing, defaults to intothevoid.online

Modify the API Dockerfile to run migrations on container startup.

The current CMD is `CMD ["node", "main.js"]`.

Create an entrypoint script approach:

1. **Do NOT modify the Dockerfile directly for migrations.**

   Instead, the deployment script already handles this via the rolling update strategy:
   - Old containers continue serving traffic
   - New containers start and run their health checks
   - Once healthy, traffic routes to new containers
   - Old containers gracefully shut down

2. **Verify the existing health check is sufficient:**
   The API Dockerfile already has:
   ```dockerfile
   HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
     CMD wget -q --spider http://localhost:3000/api/health || exit 1
   ```

   This ensures containers only receive traffic after they're healthy.

3. **For migrations, document that they should run BEFORE deploying new images.**

   Update `deploy/deploy.sh` to run migrations against the running database BEFORE updating the stack:

   Add after pulling images, before stack deploy:
   ```bash
   echo "Running database migrations..."
   # Run migrations using the new API image against the existing database
   # The migration runs in a one-off container, not affecting running services
   docker run --rm \
     --network itv_internal \
     -e DATABASE_URL="postgresql://${POSTGRES_USER:-postgres}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB:-into_the_void}" \
     "$REGISTRY/api:$TAG" \
     sh -c "cd /app && npx drizzle-kit migrate 2>/dev/null || echo 'No migrations to run'"
   ```

   Note: The exact migration command depends on how Drizzle is configured. The NX build output includes the migrations folder if it's copied.

   **Alternative: Skip automated migrations, run manually**
   For safety in production, migrations can be a manual step:
   ```bash
   # Migrations are run manually before tagging a release
   # This ensures backward-compatible schema changes
   echo "Note: Run migrations manually before deploying breaking schema changes"
   ```

The safest approach for an MVP is to:
1. Ensure schema changes are backward-compatible
2. Deploy new code first (which works with old schema)
3. Run migrations after deployment is stable
4. This is the "expand-contract" migration pattern

For this plan, update deploy.sh to document this pattern but not block on automated migrations.
