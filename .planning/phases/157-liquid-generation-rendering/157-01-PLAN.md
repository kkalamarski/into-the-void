# Plan 157-01: Liquid Generation in World-Gen & Overlay Data Transport

## Goal
After terrain generation, fill all tiles at elevation <= 0 with the biome's liquid tile as an overlay layer. Add a `liquidTiles` field to ChunkData so the client knows which tiles have liquid. Liquid tiles must NOT be blocking.

## Must-Haves (goal-backward)
- Tiles at elevation <= 0 get a liquid overlay from BIOME_LIQUID_MAP
- ChunkData carries a `liquidTiles` parallel 2D array (string[][] | null) alongside existing tiles/heights
- Liquid tiles do NOT modify the collision map (they are non-blocking)
- Liquid renders at elevation 0 regardless of terrain depth (client uses this fixed value)
- Hub biomes (stations) get NO liquid overlay

## Context
- Phase 156 created BIOME_LIQUID_MAP (biome -> liquid tile ID string) in `packages/tiles/src/definitions/liquid-tiles.ts`
- Terrain generation produces `tiles: number[][]`, `heights: number[][]`, `collisions: boolean[][]`
- Heights are clamped per-biome by BIOME_ELEVATION_RANGES — many biomes have min >= 1, so they'll naturally have no liquid
- Biomes with `min: 0` in BIOME_ELEVATION_RANGES (void_plains, fungal_forest, toxic_wastes, ancient_ruins, crystal_caves, tidal_pools, kelp_forests, deep_trenches, bioluminescent_depths, starfall_crater, miasma_marshes) can produce tiles at elevation 0
- Hub station biomes have min: 0 but should NOT get liquid
- The `tiles` array uses numeric TileId enum; liquid tiles use string IDs — keep them separate

<task id="2" title="Generate liquid overlay in terrain generation">
<context>
`packages/world-gen/src/generation/terrain.ts` has `generateTerrain()` which returns `{ tiles, heights, collisions }`.
`BIOME_LIQUID_MAP` from `@into-the-void/tiles` maps biome string -> liquid tile ID string.
Hub biomes (`canopy_station`, `ironhold_station`, `meridian_station`, `salvage_station`) should NOT get liquids.
</context>
<actions>
1. Open `packages/world-gen/src/generation/terrain.ts`
2. Import `BIOME_LIQUID_MAP` from `@into-the-void/tiles`
3. Modify `generateTerrain()` return type to include `liquidTiles: (string | null)[][]`
4. After the existing terrain loop (after `heights[y][x]` is set), add a second pass OR integrate into the existing loop:
   - Initialize `liquidTiles: (string | null)[][] = []` alongside tiles/heights/collisions
   - For each tile at (x, y):
     - Get the biome via `biomeGenerator.getBiome(worldX, worldY)`
     - If the height `heights[y][x] <= 0` AND the biome has an entry in `BIOME_LIQUID_MAP` AND the biome is NOT a hub station biome:
       - Set `liquidTiles[y][x] = BIOME_LIQUID_MAP[biome]`
     - Else: `liquidTiles[y][x] = null`
   - Do NOT modify `collisions[y][x]` — liquid is non-blocking
5. Return `liquidTiles` alongside tiles, heights, collisions
6. IMPORTANT: Do the liquid check INSIDE the existing loop to avoid a second pass. After setting `heights[y][x]`, immediately check and set `liquidTiles[y][x]`.
7. Hub biome check: biome names ending in `_station` should skip liquid. Use: `!biome.endsWith('_station')` or check against a set.
</actions>
<verify>
- `generateTerrain()` returns `{ tiles, heights, collisions, liquidTiles }`
- Tiles at elevation 0 in biomes with liquids get the correct liquid tile ID
- Tiles at elevation > 0 get null
- Hub biomes get null for all tiles
- No collision map changes — liquid tiles don't affect blocking
</verify>
</task>
