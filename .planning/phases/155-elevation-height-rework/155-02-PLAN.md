# Plan 155-02: Fix hardcoded elevation values in EntityManager and map-editor

## Objective

Replace all hardcoded `elevation * 128` calculations in EntityManager.ts (7 occurrences) and sync the map-editor's EditorScene.ts constant to 64px. Also update WorldScene.ts ENTITY_GROUND_OFFSET reference. This ensures all elevation-dependent systems (entity placement, player positioning, camera) work correctly with the new 64px step.

## must_haves

- Zero hardcoded `* 128` elevation calculations remain in EntityManager.ts
- EntityManager imports ELEVATION_HEIGHT_STEP from shared constants
- Map-editor EditorScene.ts uses 64px elevation step
- WorldScene.ts uses shared constant (if applicable)
- Player entity renders at correct height on elevated terrain
- All entity types (NPCs, features, local player) render at correct elevation

<task id="4" depends_on="1,2,3">
Verify depth sorting still works

The depth sorting formula in IsometricTransform.calculateDepth uses:
```
screen.y + (gridX * 0.0001) + (elevation * 0.1) + priorityBoost + entityOffset
```

This uses `elevation` as a logical value (0, 1, 2...) NOT pixel values, and the `elevationWeight = 0.1` is a tiny depth tiebreaker. The entityOffset is `tileHeightHalf + 1 = 65` which is tile-dimension-based, NOT elevation-step-based. So depth sorting is NOT affected by the ELEVATION_HEIGHT_STEP change.

However, verify that:
1. Entity `entityOffset = 65` still places entities in front of their own tile. With SH=64, south-face tiles extend 64px below the diamond. Entity offset 65 > 64, so entities render in front. This STILL works correctly.
2. The visual Y position change (entities at elevation 1 are now 64px higher instead of 128px) doesn't cause clipping or overlap with tile sprites at the same logical depth.

This is a visual inspection task — check that the existing depth sort values produce correct rendering with the new heights.
</task>
