# Plan 145-01: Fix ActionBar to read selectedTarget and unify target gating

## Context

The `combatStore` has two target fields:
- `targetEntityId` — set by `setInCombat(inCombat, targetEntityId)`, cleared when combat ends
- `selectedTarget` — set by `selectTarget(entityId)`, persists across combat state changes

The `ActionBar.tsx` component reads `targetEntityId` in three locations:
1. **Line 91**: `SortableAbilitySlot` component subscribes to `state.targetEntityId`
2. **Line 122-125**: Click handler sends `targetEntityId` in the `ability:use` emit
3. **Line 179**: `ActionBar` component subscribes to `state.targetEntityId`
4. **Line 258-261**: Keyboard handler sends `targetEntityId` in the `ability:use` emit

When `setInCombat(false)` is called (creature dies, player dies, etc.), `targetEntityId` becomes `null` while `selectedTarget` may still point to a valid entity. This means:
- Pressing an ability keybind after selecting a creature sends `targetEntityId: undefined` to the server
- The server rejects the ability because `requiresTarget: true` abilities fail with "Ability requires a target"
- This breaks both combat abilities (TARGET-01) and keyboard-triggered gathering (TARGET-02)

Additionally, the `TargetFrame.tsx` component reads `targetEntityId` to show the target health frame. It should also read `selectedTarget` for consistency — the target frame should show whichever entity the player clicked.

Also, `game.gateway.ts` has debug `console.log` statements in the `ability:use` handler that should be removed (this partially addresses MISC-03 scope, but these are in the ability handler not entity click handler — the full MISC-03 cleanup is Phase 146).

## must_haves

Derived from phase goal backward:

1. **ActionBar reads selectedTarget** — The `ability:use` emit in both click and keyboard handlers passes `selectedTarget` from `combatStore`, not `targetEntityId`. This is the root cause of TARGET-01.
2. **No ability fires with null target when entity is selected** — When `selectedTarget` is non-null and the ability has `requiresTarget: true`, the emitted payload includes the selected entity ID. This gates correctly: if `selectedTarget` is null, no targetEntityId is sent, and the server rejects the ability with "Ability requires a target".
3. **Gathering via action bar works** — Because the gather ability has `requiresTarget: true`, and the ActionBar now reads `selectedTarget` (which is set when clicking a resource node in WorldScene), pressing the gather keybind on a selected resource sends the correct targetEntityId to the server. This satisfies TARGET-02 for keyboard-triggered gathering. (Click-triggered gathering in WorldScene already works because it passes entityId directly.)
4. **TargetFrame shows clicked entity** — The TargetFrame reads `selectedTarget` matching what the ActionBar reads, so the UI is consistent about which entity is "targeted".
5. **Debug logs removed** — No `console.log` statements remain in the ability:use gateway handler or the useAbility service method.
